### Defect repaired

When a background read-model rebuild failed, a 30-second retry suppression window could cause the next load to reuse the last-known view without exposing the failure. The page could therefore look current even though the requested rebuild was unavailable.

The read model now carries an explicit `ready | refreshing | unavailable` status. Failed or suppressed rebuilds retain the safe last-known docket but show `Today refresh unavailable · showing the last verified view`. This is independent of the Gmail evidence freshness label. A successful rebuild clears the unavailable state.

## Sterling publisher readiness requirements

The publisher must remain off until all of the following are implemented and accepted.

### Fresh evidence ingestion

- A publisher run must start from a successful Gmail incremental sync, not fixture data.
- Record the sync start/end, Gmail history/checkpoint, relevant thread/message coverage, and source errors durably.
- Require evidence ingestion to have succeeded within 15 minutes of assembly; fail closed on partial coverage, checkpoint gaps, or unavailable Gmail.

### Source watermarks

- Use one opaque, reproducible watermark covering the Gmail checkpoint and relevant message IDs, canonical Projects/Jobs versions, candidate reviews/founder corrections, and time-dependent boundaries such as snooze expiry.
- Capture it before assembly and compare it immediately before publication. If any component changes, discard the proposal and rebuild.
- Store the watermark with the publication and require the reader to validate it. Never relabel an older publication with a newer watermark.

### Publication expiration

The current 15-minute publisher TTL is safe but incompatible with the intended daily cadence. Use an explicit schedule-derived expiry with a 45-minute late-run grace:

- 6:00 a.m. publication expires at 10:15 a.m.
- 9:30 a.m. publication expires at 1:15 p.m.
- 12:30 p.m. publication expires at 3:15 p.m.
- 2:30 p.m. publication expires at 4:45 p.m.
- 4:00 p.m. publication expires at 8:00 p.m.; after that, use canonical fallback until the next successful 6:00 a.m. run.

Expiry must be fixed when the publication is created. A missed run must not extend or roll forward old Sterling evidence, and an expired row must never appear current.

### Legacy fallback

- Immediately use canonical Today when no publication exists or when a publication is expired, malformed, validation-failed, watermark-mismatched, or based on incomplete evidence.
- Label fallback as canonical and never imply Sterling verification.
- Keep the last verified canonical view visible with a clear unavailable/refreshing state when its rebuild fails.

### Founder refresh

- An authenticated founder refresh should initiate one idempotent flow: ingest fresh evidence, reconcile canonical state, assemble and validate Sterling, then publish only on PASS.
- Use the existing durable lease/idempotency infrastructure and expose progress or failure.
- Refresh must never merely extend `expires_at` or reuse an old evidence watermark.

### Scheduled reconciliation

- Only after approval, use the existing authenticated Vercel cron infrastructure with a durable lease, idempotency key, bounded retries, and a durable run record.
- Reconcile before every scheduled publication. Run full evidence/identity reconciliation at the first and last cadence points, with bounded incremental reconciliation at intermediate points.
- Publish only after ingestion, coverage, validation, watermark recheck, and canonical reconciliation all pass. Otherwise retain canonical fallback and record the failure visibly.
